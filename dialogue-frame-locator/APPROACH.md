# Approach

A short narrative version of this project. Full depth — assumptions, interfaces,
threshold values, testing strategy, phased roadmap — lives in
[`../DESIGN.md`](../DESIGN.md); this document is the five-minute version that
points back there instead of restating it.

## The problem, as understood

Given a video URL and a target line of dialogue, find the exact frame where
that line is first spoken, and return the timestamp, frame number, the text
actually recognized, the frame image, and a confidence/status — without a
human watching the video.

The assignment's wording ("on-screen dialogue appears", "extracts the text")
reads OCR-flavored, but the one worked example (an ok.ru clip, "My mind
rebels at stagnation") is spoken audio with no burned-in text. Rather than
silently pick a reading, the design treats this as a stated assumption
(DESIGN.md A1): **this build is spoken-dialogue search via ASR**, with OCR
designed in as a first-class, pluggable `Detector` that isn't implemented
yet. If an eval video turns out to be subtitle-only, adding OCR is one new
class behind an existing interface, not a rewrite — see DESIGN.md §20 for
the full defense of that scope call.

## Decisions that actually mattered

**ASR-first, OCR deferred.** Covered above — the single biggest scope call
in the project, and the one most likely to get pushback in review.

**Cloud-primary ASR (pinned OpenRouter Whisper-large-v3) with a local
`faster-whisper` fallback, both behind one `AsrProvider` interface.** Pinning
the backing host (not leaving it to OpenRouter's auto-routing) is what
actually gets word-level timestamps back — auto-routing can silently
downgrade to segment-only ones, which would break onset localization
entirely. The local fallback exists so a single provider outage doesn't
fail the run. Cost: even pinned, OpenRouter's routing can drift the exact
underlying model version over time, so reproducibility is weaker than a
fully-local pinned model — named as a residual risk (DESIGN.md A9), not
engineered away. Every request is chunked (~22s, 1.5s overlap) regardless of
clip length, because the cloud endpoint enforces a hard per-request
timeout — this is a correctness constraint, not a long-video optimization
(DESIGN.md A10, §7.5).

**Frame mapping via actual decoded PTS + keyframe-seek, never
`round(t * fps)`.** fps arithmetic quietly breaks on variable-frame-rate
video and on containers whose timeline doesn't start at zero — both real
cases, not edge cases invented for the spec. The fixed convention is: the
frame on screen at `t` is the one with the greatest PTS ≤ `t`. On a
genuinely VFR stream, `frame_number` is reported as `null` rather than a
fabricated integer (the assignment's own "where applicable," D3). See
DESIGN.md §9 for the two-timeline (audio vs. container) bookkeeping this
requires — it's the part most likely to be an off-by-several-frames bug if
skipped.

**Graded matching (fuzzy + phonetic, semantic as a guard) with an explicit
`AMBIGUOUS` status.** ASR transcripts are never exact strings, so matching
can't be exact-match-or-nothing — but it also can't accept anything
"close enough" (`matched_text` always shows what was actually recognized,
so a fuzzy accept like "at" vs. "against" is visible, not hidden). When two
occurrences of the phrase are comparably strong, the system reports both and
says `AMBIGUOUS` rather than silently picking the earliest — see DESIGN.md
§8 and §10 for the threshold policy and the reasoning for treating
uncertainty as a first-class output.

## Deliberately out of scope

OCR (deferred, see above — the seam exists), a job queue / concurrent
processing (this is a one-video-at-a-time interview task; ASR is the long
pole if that ever changes), an HTTP API (CLI is the only interface), and
production hardening (rate limiting, auth, enterprise sandboxing). DESIGN.md
§2.3 and §13 cover the full list and what each would take to add.
